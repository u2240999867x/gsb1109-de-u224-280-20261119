# 两家供应商 Call Activity 汇合丢行：可复跑排查包

本目录是一个**只做定位与取证、不改业务流程行为**的诊断工程，基于仓库当前
SpiffWorkflow 快照构建。它复现“甲、乙两个统计子流程汇入父流程后，报表有时只剩
一家”的场景，并给出可在本地重复的采样办法。

## 复跑命令

```bash
# 从仓库根目录、使用仓库自带虚拟环境
.venv/bin/python -m pytest investigation/tests -v          # 11 项证据断言
.venv/bin/python -m investigation.diagnosis.run_demo       # 中文排查报告 + JSON 采样
```

`run_demo` 会重新从 BPMN 启动工作流，并把机器可读证据写到
`investigation/samples/diagnosis_matrix.json`。整个过程不修改 `SpiffWorkflow/`
下任何库代码，也不修改 BPMN 的执行语义。

## 目录结构

- `bpmn/no_io/`：父流程 + 甲/乙子流程，Call Activity **不声明** IO 规范。
- `bpmn/io_total/`：同样的操作，但两个 Call Activity **只声明 `total` 输出**。
- `diagnosis/harness.py`：加载、驱动、公开快照、JSON 存档/恢复、（仅实验室）别名探针。
- `diagnosis/scenarios.py`：三个检查点与对照场景的结构化证据。
- `diagnosis/run_demo.py`：可运行入口。
- `tests/test_diagnosis_evidence.py`：把每条观测固化成断言。

## 场景设定

- `total.rows` 初始为 `[A:0, B:0]`。
- 甲在自己的 Call Activity 内把 A 改成 11，并 `reverse()` 调换两行。
- 乙把 B 改成 19，并用列表推导在自己的返回数据里去掉过期的 A（只剩 B 一行）。
- 两个子流程各放两个 `manualTask` 屏障（入口、编辑后），用于确定性地控制交错与
  完成顺序；引擎步骤本身照常自动执行。

## 两类证据，严格分开

- **公开观测（可用于旧故障材料）**：任务状态 + `deepcopy` 的任务数据，不含任何
  对象地址。生产平台对一次历史运行能保留的只有这一类。
- **同一性探针（LAB-ONLY）**：`id()/is` 得到的嵌套容器别名关系。对象地址无法离线
  获取、也过不了序列化，这里只用它演示“公开数据 alone 能证明什么、不能证明什么”。

## 三个检查点的实测结论

### 检查点一：甲调换完、乙还没动

- live 与“该时刻存档再恢复”的**公开数据完全一致**，都是 `[B:0, A:11]`。
- LAB-ONLY：live 时父流程与两个子流程的相关任务共享**同一个 `rows` 列表对象**；
  JSON 恢复后，父/子之间的共享被切断，别名拓扑被重建，但值不变。
- 因此：仅凭此检查点的公开数据和那一份序列化文件，只能证明双方看到相同的值与
  顺序，**不能判定它们是否为同一嵌套对象**。

### 检查点二：同一完成顺序（先甲后乙），在任一返回之前看甲的数据

| 续跑方式 | 乙编辑后、返回前甲视角 A.count | 最终 counts |
| --- | --- | --- |
| live（甲调换后直接继续） | 19 | `[0, 19]` |
| restored（从该时刻存档恢复再继续） | 11 | `[0, 11]` |

操作次序完全相同，仅“是否经过一次序列化往返”不同，结果分叉。live 中乙对共享
`rows` 的就地改写（写索引 1）在返回前就污染了甲尚未返回的数据；恢复后别名被
切断，污染不再发生。

### 检查点三：反序完成（先乙后甲）

- live 与 restored **最终都只剩 `[B:0]` 这一行**。
- 但返回前甲视角 A.count 分别是 19 与 11。
- 即：**相同的最终一行，背后是发生在不同阶段的不同故障**。只看最终报表无法区分。

## 三个候选机制与判别方法

| 机制 | 发生阶段 | 判别所需观测 | 本工程实测 |
| --- | --- | --- | --- |
| 运行期嵌套数据串变（别名污染） | 乙编辑后、任一 Call Activity 返回前 | 甲在返回前的一条 `total.rows` 公开采样 | live A.count=19；restored=11 |
| 序列化的状态重建 | 存档 → 恢复 | 受控续跑：同操作次序下 live 与 restored 是否分叉 | 公开值往返不变，但父子别名被切断，下游结果改变 |
| 最终汇合覆盖（列表截断） | 并行网关 join | join 前两分支行数 vs 最终行数 | 甲 2 行、乙 1 行，最终被截成 1 行 |

源码依据：

- 入口浅引用、无 IO 时整体 `deepcopy` 返回：
  `SpiffWorkflow/bpmn/specs/mixins/subworkflow_task.py` 的
  `CallActivity.copy_data` / `update_data`。
- 任务数据继承对可变对象只做浅 `copy`：
  `SpiffWorkflow/util/deep_merge.py` 的 `DeepMerge.merge`。
- 汇合按位置合并列表并截断：同文件 `merge_array` 末尾的
  `del a[len(b):]`，由 `SpiffWorkflow/bpmn/specs/mixins/unstructured_join.py`
  的 `_run_hook` 调用。

隔离实验（`scenarios.merge_truncation_evidence`）：两行目标并入一行输入会被截成
一行；一行目标并入两行输入则追加、不丢行。所以“最终少 A”的直接机械原因是 join
截断，它与运行期别名污染是**两个可独立发生、阶段不同**的机制。

## 只声明 `total` 输出的对照（io_total）

- 入口侧别名**没有被消除**：live 续跑在返回前照样出现 A.count 11→19。
  原因是没有声明 dataInput 时 `copy_data` 仍把全部数据按引用传入。
- 变化只在**返回边界**：命名输出经 `var.set` 回拷（rows 仍是同一对象的引用），
  且父调用任务会保留与 `total` 无关的变量（`audit_tag`）；无 IO 版则整体
  `deepcopy` 覆盖、`audit_tag` 丢失。
- 结论：给 Call Activity 加“只输出 total”的 IO 声明改变的是返回范围与返回拷贝
  语义，**并不能单独阻止运行期的跨分支串变**。

## 现有材料何时足以判定，何时必须受控续跑

足以判定：

- 若持有“任一返回之前”甲分支的公开 `total.rows` 采样：A.count 已变 19 而甲未再
  写入，即可仅凭公开值判定运行期串变，不需要对象地址。
- 若 join 前两个分支的公开行数已知（甲 2 行、乙 1 行）而最终只剩 1 行，即可判定
  汇合阶段发生了列表截断覆盖。
- 若序列化文件可在本地无损往返，且恢复后续跑不再出现污染，可判定故障与序列化的
  状态重建（别名拓扑改变）相关。

不足、需要受控续跑：

- 只有最终报表缺 A、没有任何 join 前中间采样时，无法区分：乙返回值本身只有一行
  导致的截断、运行期别名污染、序列化重建后再汇合这三条路径——它们最终都可能只剩
  `[B]`。
- 因此在没有对象地址或前序采样的旧材料上，**不能从“最终缺少 A”就断言是合并写
  丢的**。

## 给配置人员的最小补观测（二选一即可打破不可区分性）

1. 最小一条观测：在**任一 Call Activity 返回之前**，补采甲分支（甲的 `a_park`
   或其父调用任务）的 `total.rows`。
   - A.count == 19：运行期嵌套数据串变已发生。
   - A.count == 11：串变未发生，缺 A 来自汇合截断。
2. 或一次可重复的受控续跑：在“甲调换完、乙未动”的检查点存档，保持相同操作次序
   与完成顺序，分别跑 (i) 直接继续、(ii) 反序列化后再继续，比较 join 前甲的采样
   与最终报表。两者分叉即证明序列化重建改变了别名拓扑。

本工程的 manualTask 屏障与 `harness.complete_manual` / `archive` / `restore`
就是上述两种采样的现成实现，可直接套用到真实流程定义上。
