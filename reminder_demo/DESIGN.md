# 供应商缺件提醒：设计与论证

基于 SpiffWorkflow BPMN 执行器，不改执行器内核。运行轨迹：

```bash
.venv/bin/python -m reminder_demo.run_scenarios
```

## 1. 流程模型（reminder_plan.bpmn）

每个批次一个独立流程实例（提醒计划按批次独立，甲的保存/恢复不触碰乙）：

- 并行三支路：`wait_data`（消息 `docs_data`）、`wait_validation`（消息 `docs_validation`）、
  `reminder_plan` 子流程。两份文件都到齐 → `released`（terminate 结束事件）取消提醒支路。
- `reminder_plan`：`due_timer`（timeDate = 数据里的 `due_time_iso`）→ `dispatch_reminder`
  （人工任务）→ 网关（`dispatched == True`？）→ `wait_confirm`（消息 `delivery_confirmed`）→ 结束。
- 续期：`reminder_plan` 上的中断边界消息 `renewal_requested` → `apply_renewal`（人工任务）
  → 汇合网关 → 重新进入 `reminder_plan`。只重建提醒子流程，两条文件支路不动
  （续期不撤销已收文件）。每批只许一次，由调度器在收件口拒绝第二次。
- 到期时点存在定时器任务的 `internal_data.event_value` 里且只求值一次，所以续期不靠改旧
  定时器，而是让边界事件中断旧子流程、用新数据生成新定时器任务——这是不改内核的关键手法。

真实等待点（都是引擎真实状态，轨迹里每轮打印、可用 `get_tasks` 核对）：

| 等待点 | 状态 | 含义 |
|---|---|---|
| `due_timer` | WAITING | 定时等待，到期时点在任务 internal_data 里 |
| `dispatch_reminder` | READY | 提醒已可执行但还没发（人工任务，等派发器） |
| `wait_confirm` | WAITING | 已派发、等待送达确认 |
| `apply_renewal` | READY | 续期请求已捕获、等待应用 |
| `wait_data` / `wait_validation` | WAITING | 等待文件 |

## 2. 轮转顺序（driver.py `run_round`，每轮严格按序）

1. 投送收件箱事件（文件消息/续期请求；批次内按提交顺序，批次间按批次号排序）
2. 引擎推进（`refresh_timers` + `do_engine_steps`；到期钩子登记 PLANNED 台账）
3. 应用续期（READY 的 `apply_renewal`）——先于派发，故同轮内续期优先
4. 派发决策（READY 的 `dispatch_reminder`）——全流程唯一发送点
5. 对账（就 DISPATCHED 未确认条目查询通知服务；服务可能回 UNKNOWN）
6. 通知服务推进（到点的已接受派发在此真正发出）
7. 生成值班员看板快照

## 3. 证据模型

- 幂等键：`{批次}#r{版本}`，派发时交给通知服务；同键重复提交不会产生第二次发送。
- 台账（每批次一本，随该批次工作流一起 `serialize_json`/`deserialize_json`）：
  PLANNED → DISPATCHED → CONFIRMED_SENT；旁路终态 CANCELLED（续期撤销）、
  SUPERSEDED（未派发即被取代）、SUPPRESSED（被证据拦下）、VOID（文件已齐）、LOST（服务无记录）。
- 通知服务（外部世界，不回滚）：`submit`/`cancel`/`query`，可延迟确认，
  降级窗口内 `query`/`cancel` 只回 UNKNOWN。
- 决策规则（派发前必过）：文件已齐→VOID；已有 CONFIRMED_SENT→SUPPRESSED；
  有 DISPATCHED 未确认→先向服务取证：SENT→封盘停发；ACCEPTED→等送达不重复发；
  UNKNOWN→置"待核对"保守停发；CANCELLED/NOT_FOUND→确定未发，可发新提醒。

## 4. 三次保存/恢复轨迹（run_scenarios.py，全部核对通过）

- 恢复一：旧派发已交服务但未真正发送（延迟发送）。续期 → `cancel` 成功 → r1=CANCELLED
  （终态证据入台账）→ 保存 → 恢复（服务降级只回 UNKNOWN）→ 新时点仍缺件 → 只发 r2。
  关键：恢复后不需要再向服务证明 r1 未发——撤销证据已在台账里。
- 恢复二：旧派发已实际发出但确认丢失（台账停在 DISPATCHED）。保存 → 恢复（服务降级）
  → 续期时 `cancel` 得 UNKNOWN → 待核对、保守停发 → 新时点派发决策取证仍 UNKNOWN →
  r2 被拦下 → 服务恢复后对账确认 r1 已送达 → 封盘。全程实际发送记录只有 r1 一条。
- 恢复三：旧提醒 READY 未发（派发器暂停）。保存 → 恢复（派发任务仍 READY）→ 续期中断
  旧子流程（r1=SUPERSEDED）→ 甲补齐校验件 → 放行 terminate 取消新定时器 →
  旧、新两条都没发。
- 三个场景里乙都按自己的事件顺序运行（到期→派发→送达→收齐放行），甲的三次恢复
  不换乙的实例、不回滚乙的台账，乙始终只发一条。

## 5. 不可能性论证：缺了发送身份和接受查询，第一次与第二次不可兼得

设两个世界在恢复后的引擎信息状态完全不可区分：

- W1：旧提醒未实际发送（恢复一的情形）——性质一要求新提醒最终要发（且只发它）。
- W2：旧提醒已实际发出但确认丢失（恢复二的情形）——性质二要求任何时点都不再发第二条。

若通知端 (a) 不提供可恢复的发送身份（没有幂等键，执行器连"哪一次派发"都无法命名，
重试在服务端就是一次新发送），且 (b) 不能查询原接受（问不出"你收没收到过 X"），
则恢复后执行器在 W1、W2 中的全部可用信息相同：工作流状态、数据、到期时间都一样，
外部事实（发没发）不进状态。任何决策规则都是信息状态的函数，同一状态只能给出同一
结论：判"发"则 W2 出现第二条（违反性质二）；判"不发"则 W1 的新提醒永远不发
（违反性质一）。故两条性质不可兼得。∎

补上任一能力即可区分两个世界：有可恢复身份 + 幂等接收（同键重发安全、撤销有确定
语义），或有接受查询（UNKNOWN 时保守停发、恢复后取证）。本设计的台账 + 幂等键 +
cancel/query 正是这两条的具体化。

## 6. 值班员呈现（待核对期间继续接收文件）

- 看板按批次一行：文件齐缺、当前等待点、台账各版本状态、标志位。
- 待核对时显示"待核对·发送隔离中（文件接收照常）"：隔离的只是发送动作，
  文件消息照常捕获、齐件照常放行（场景二轮次 4：甲待核对的同时乙收齐放行）。
- 对账每轮自动重查；服务恢复后自动消解（SENT→封盘；CANCELLED/NOT_FOUND→解除隔离，
  必要时由值班员补发）。提供"立即重查"和"人工确认已送达"两个动作，人工结论连同
  证据来源（query / cancel / 人工）写入台账 history，可审计。

## 7. 为什么任务状态或最新到期时间不能代替发送证据

- 保存时的可执行任务状态（READY/WAITING）记录的是引擎的意图，不是外部世界的事实。
  崩溃可能发生在"任务 READY"与"服务真正发出"之间任意一侧：状态说没发，信件可能已
  在供应商信箱；状态说已派发，服务可能根本没收到。恢复/重置还能改写状态——它不是
  服务世界的证人。
- 最新到期时间是调度值，只说"何时可以发"，不含"是否已经发"的那一位。续期后比较
  到期时间，分不出"旧发送已执行"与"旧发送未执行"——两种情形共享同一个旧到期时间。
- 发送证据必须锚定在交接点上：要么是执行器能带着过恢复、服务端能据以幂等的身份
  （幂等键），要么是服务端可查询的接受记录。只有它们能把 W1 和 W2 分开。
